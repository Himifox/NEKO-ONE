# NEKO-ONE 产品路线图

> 状态：当前执行计划
>
> 更新日期：2026-08-15
>
> 适用范围：NEKO-ONE 公共房间 Web 产品

## 1. 文档目的

本文定义 NEKO-ONE 从单房间 Alpha 到可持续公开运营产品的阶段、交付物和验收门槛。

[公共房间架构设计](design/public-room-web-architecture.md#19-交付阶段)中的 Phase 0–4 描述的是从旧桌面工程迁移代码的顺序；本文的“产品阶段 1–5”描述迁移之后的发布和运营路线。两者不是同一套阶段编号。

路线图遵守以下原则：

1. **先验证人格连续性，再增加入口。** 记忆隔离、回复目标和房间节奏没有稳定前，不接入更多平台。
2. **先完成单实例闭环，再水平扩容。** 没有真实容量证据时，不提前引入 Redis、PostgreSQL 或微服务复杂度。
3. **默认保护访客。** 身份绑定、记忆保留、数据导出和遗忘必须由明确规则控制，不能靠显示名或模型猜测身份。
4. **服务器是唯一事实源。** 主动主持、消息顺序、Persona、记忆写入、表情和共享语音都由服务器统一决定。
5. **不恢复被裁剪的桌面生态。** Agent、插件市场、电脑控制、游戏和替代渲染器不因后续扩展重新混入核心运行时。

## 2. 阶段总览

| 阶段 | 版本目标 | 核心结果 | 当前状态 |
| --- | --- | --- | --- |
| **阶段 1：单房间 Alpha** | `v0.1` | 建立可运行、可管理、可部署的公共房间基线 | **代码完成，待公网验收** |
| **阶段 2：公网 Beta** | `v0.2` | 补齐安全、审核、可观测性、备份与容量证据 | 未开始 |
| **阶段 3：身份与关系** | `v0.3` | 从匿名 Cookie 演进到可恢复账号与记忆自主权 | 未开始 |

## 3. 阶段 1：单房间 Alpha（v0.1）

### 3.1 目标

证明一个服务器唯一的 NEKO 可以同时面对多位访客，并在不泄露身份与记忆的前提下，持续输出一致的文字、表情和声音。

### 3.2 已完成范围

- 单个 `main` 公共房间与游客 Cookie 身份；
- 多访客 WebSocket、心跳、自动重连和按 `room_seq` 续传；
- `request_id` 幂等发送、单写入者消息队列和单一 generation；
- `RoomDirector` 回复对象选择、冷却、公平性和重复抑制；
- 多供应商文本模型适配与流式输出；
- 房间共享记忆、访客独立记忆和管理员保护 Persona；
- Live2D 情绪状态与全房间共享 TTS；
- Persona、公共事实、访客记忆、封禁、消息状态、限额和审计管理；
- SQLite 持久化、Nginx/systemd 示例与公网边界验证脚本；
- 桌面端、Agent、插件、游戏、ASR、VRM、MMD 和 PNGTuber 入口移除。

### 3.3 退出前必须完成

以下工作决定 `v0.1` 能否从“代码完成”变为“可公开试用”：

- [ ] 使用真实 LLM、Memory 和至少一个 TTS 供应商完成端到端验收；
- [x] 运行 10、25、50 人三个并发档位的 30 分钟房间模拟；
- [ ] 完成至少 24 小时单实例稳定性运行，确认无任务泄漏和数据库锁死；
- [x] 验证 LLM、Memory、TTS 分别不可用时的降级行为；
- [ ] 在独立 Debian 主机恢复一次公共数据库、记忆与私有配置备份；
- [ ] 确认 Live2D 模型、动作、字体和公开音色的公网使用许可；
- [x] 清退无来源角色包和旧渲染库，为仓库浏览器运行库建立许可证、来源与 SHA-256 清单；
- [x] 为 Nginx 补齐 CSP、安全响应头、连接上限和请求体上限；
- [x] 确定聊天记录、访客记忆、审计日志和音频文件的保留周期，并实现失败可重试的自动清理；
- [x] 增加暂停房间、只读模式、关闭主动主持和取消 generation 的应急开关；

### 3.4 退出门槛

- 50 个模拟访客下始终只有一个主写入者和一个 NEKO generation；
- 消息无重复、无逆序，断线续传后客户端时间线一致；
- A 访客的独立记忆不会出现在回复 B 的上下文或管理查询中；
- 访客输入无法修改 Persona，也无法读取密钥和内部服务地址；
- 依赖故障不会让房间进程崩溃，文字、语音与记忆按设计分别降级；
- 备份能够恢复，管理员能够执行封禁、遗忘和紧急停用；
- 公开资产授权清晰，生产环境只暴露 TCP 443。

### 3.5 本阶段明确不做

账号注册、多房间、多实例、直播平台接入、礼物事件、公开音色配置和实时语音输入。

## 4. 阶段 2：公网 Beta（v0.2）

### 4.1 目标

让单房间从“可以部署”变成“可以持续运营”：出现滥用、供应商故障、成本突增或数据损坏时，管理员能够发现、限制、恢复并解释发生了什么。

### 4.2 功能与工程范围

#### 安全与内容治理

- 输入和输出内容审核，明确超时、供应商故障与高风险内容的 fail-open/fail-closed 策略；
- IP、访客、房间和供应商预算四层限流；
- 慢速模式、房间只读、暂停、断开指定访客和取消当前生成；
- 举报队列、处理原因、处分期限与申诉记录；
- 管理员重新认证、会话轮换、操作审计导出和可选 MFA；
- CSP、HSTS、安全 Cookie、可信代理、WebSocket Origin 和上传边界检查。

#### 可观测性与成本

- 结构化日志，统一 `room_id`、`turn_id`、`visitor_id_hash`、`provider` 和 `reason_code`；
- 在线人数、队列深度、首 token 延迟、生成耗时、TTS 耗时和错误率指标；
- 每轮 token、TTS 字符数和估算成本记录；
- 日/小时硬预算，超额时停用主动主持或切换只读；
- 就绪检查覆盖 SQLite、Memory 和必要的私有配置状态；
- 告警覆盖进程退出、错误率、队列堆积、磁盘空间和备份失败。

#### 数据与可靠性

- 数据库 schema 版本和向前迁移脚本；
- Persona 版本历史、差异查看与一键回滚；
- 记忆、消息、审计和共享音频的自动保留/清理任务；
- 每日备份、校验、异机恢复和恢复时间记录；
- 24/72 小时 soak test 与 LLM/Memory/TTS 故障注入；
- 移动端、键盘操作、减少动态效果和基础无障碍检查。

### 4.3 验收门槛

- 目标 10–50 人房间连续运行 72 小时，无顺序破坏、死锁或不可恢复队列；
- 管理员能在一个后台完成发现、限流、封禁、审核、回滚和恢复；
- 成本超过设定预算后自动停止非必要模型/TTS 调用；
- 所有修改 Persona、共享记忆和访客状态的操作都有操作者、时间、原因和结果；
- 数据保留任务可重复执行，备份恢复演练成功；
- 完成一次面向公网配置的安全复核，并关闭所有未列入 allowlist 的路由。

### 4.4 本阶段明确不做

不为了“看起来能扩容”提前拆数据库；不引入公开插件执行、浏览器控制、任意文件上传或访客自定义模型密钥。

## 5. 阶段 3：身份与关系（v0.3）

### 5.1 目标

让愿意长期参与的访客拥有可恢复身份、明确的记忆控制权和跨设备连续关系，同时保留无需注册即可进入的低门槛体验。

### 5.2 计划范围

- 可恢复账号登录与登出，供应商选择通过 ADR 决定；
- 匿名身份显式绑定账号，要求重新认证并记录审计；
- `guest`、`member`、`moderator`、`admin` 四级权限；
- 访客查看、导出、纠正和删除自己的独立记忆；
- 记忆保存同意、保留期限和撤回机制；
- 显示名历史、防冒充规则和管理员备注；
- 封禁申诉、账号恢复和高风险操作二次验证；
- 关系状态只从有来源的事实与反思演进，不用模型猜测自动合并身份。

### 5.3 数据约束

- 匿名 Cookie、账号和内部 memory subject 使用不同标识；
- 绑定是显式事务，失败时全部回滚；
- 不使用 IP、User-Agent、显示名或语言风格判断两个人是否相同；
- 账号删除必须覆盖身份、独立记忆、会话和可识别审计字段的处理策略；
- 房间公开消息与个人独立记忆仍是两个数据域。

### 5.4 验收门槛

- 匿名访客可以安全升级为账号，跨设备恢复后只获得自己的记忆；
- 绑定、解绑、导出、遗忘和账号删除均有自动化验收与审计；
- moderator 无法编辑 Persona、读取密钥或访问不属于其职责的数据；
- 删除请求在规定时间内完成，并能给出不泄露内部信息的处理结果。

### 5.5 本阶段明确不做

不加入私信、关注流、用户生成角色、开放插件或 NEKO Persona 市场。

## 6. 阶段 4：多房间与扩容（v0.4）

### 6.1 启动条件

只有满足以下任一条件才开始本阶段：

- 单实例容量测试证明无法满足真实峰值；
- 需要故障转移或滚动发布，单进程停机窗口不可接受；
- 产品明确需要多个彼此隔离的房间。

### 6.2 计划范围

- 房间创建、关闭、暂停、归档与容量配置；
- 一个统一 NEKO Persona 下的房间局部上下文，禁止房间分叉人格；
- PostgreSQL 保存消息、事件、身份、审核和配置版本；
- Redis 保存短期在线状态、跨实例发布和房间租约；
- 对象存储保存共享 TTS 和允许公开的角色资源；
- `tts-worker` 与 Conversation worker 可独立伸缩；
- 房间 owner lease、单调 fencing token 和写入校验；
- schema、消息协议和事件回放的滚动升级兼容策略；
- 从 SQLite 到 PostgreSQL 的校验式迁移和可执行回滚方案。

### 6.3 关键不变量

```text
每个房间同一时刻只有一个有效写入者
旧租约持有者不能在切换后继续写入
消息序号在故障转移前后保持单调
Persona 是全局受保护层，房间只能拥有局部上下文
```

仅增加 Redis 分布式锁而没有 fencing token，不算完成多实例设计。

### 6.4 验收门槛

- 主实例在生成中退出后，新实例能接管房间且不会产生双回复；
- 故障转移、重放和滚动发布不产生重复 `room_seq`；
- 房间、访客和 Persona 三层记忆在多实例下仍严格隔离；
- SQLite 迁移结果经过数量、哈希和抽样语义校验；
- 运行成本、容量上限和回滚时间有真实演练数据。

## 7. 阶段 5：1.0 产品化

### 7.1 目标

把经过验证的公共房间能力包装成有稳定契约、可嵌入博客、可长期维护的正式产品。

### 7.2 计划范围

- `pardofelis-web` 到 `https://neko.pardofelis.wiki/` 的稳定链接入口；iframe 或组件嵌入保留为后续独立决策；
- 稳定的 HTTP/WebSocket 协议版本、弃用周期和升级说明；
- 管理员操作手册、事故响应、备份恢复和数据请求流程；
- 服务状态页、维护窗口和变更日志；
- 经过许可审核的公开 Live2D/TTS 资源管理；
- 可选的直播平台**消息输入适配器**，只把平台事件标准化为公共房间事件；
- 发布检查表、容量基线、安全复核和隐私说明。

### 7.3 仍然不进入核心的能力

- 通用 Agent 与任意工具执行；
- 浏览器、桌面或文件系统控制；
- 插件市场、Steam/Workshop 与云存档；
- 游戏、Galgame、截图/OCR 和桌面教程；
- VRM、MMD、PNGTuber 和桌面启动器；
- 未取得公开授权的声音克隆和角色资源。

### 7.4 1.0 发布门槛

- 至少完成一次 Beta → 1.0 的真实数据迁移演练；
- 协议、数据保留、隐私、备份和事故处理都有公开或内部可执行文档；
- 目标容量下的稳定性、安全、成本和恢复指标连续满足一个发布周期；
- 核心功能不依赖任何被列为“明确不进入核心”的模块。

## 8. 跨阶段工作流

每个阶段都按同一顺序推进：

1. **ADR**：对身份、隐私、协议、存储和供应商等不可逆选择先写决策记录；
2. **Schema/协议**：先定义迁移、兼容和错误行为，再修改实现；
3. **最小实现**：保持单一事实源，不同时保留新旧两套长期路径；
4. **验证**：单元级检查、端到端验证、故障注入、容量与恢复演练；
5. **灰度**：用功能开关和预算限制小范围开放；
6. **退出评审**：逐项核对阶段门槛，记录未完成项及接受风险；
7. **发布**：更新 README、部署文档、变更日志和回滚步骤。

## 9. 优先级与变更规则

优先级定义：

- **P0**：身份/记忆泄露、Persona 投毒、双写、密钥暴露、无法恢复的数据损坏；
- **P1**：房间不可用、消息乱序、无限成本、管理能力缺失和主要无障碍阻塞；
- **P2**：体验优化、新供应商、运营效率和非关键视觉增强；
- **P3**：尚未被真实需求证明的扩展能力。

任何新功能如果降低记忆隔离、单写者、安全或恢复能力，必须暂停并重新做 ADR。阶段范围可以调整，但上述核心不变量不能为了赶版本被降级。

## 10. 下一步执行清单

当前只启动阶段 1 的退出工作，顺序如下：

1. 使用已落地的费用闸门和隔离清理流程完成真实供应商端到端冒烟并保存证据；
2. 执行已落地的 50 人 24 小时稳定性方案，并保存证据；
3. 审核公开模型、动作、字体和声音授权；
4. 在独立 Debian 主机执行已落地的备份恢复流程并记录恢复时间；
5. 召开阶段 1 退出评审，决定是否进入公网 Beta。
