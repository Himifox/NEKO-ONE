# NEKO-ONE 分阶段实施计划

> 文档状态：执行中
>
> 更新日期：2026-08-15
>
> 适用范围：NEKO-ONE 公共聊天 Web 产品
>
> 产品路线：详见[产品路线图](../roadmap.md)

## 1. 计划目标

NEKO-ONE 不再延续原项目“桌面宠物 + 直播 + 插件 + Agent + 游戏 + 多渲染器”的综合运行时路线，而是在现有代码基础上持续做减法，并围绕一个目标重新收束：

> 一个拥有身体、连续记忆，能辨认不同访客并主持公共房间的长期在线实体。

本计划用于指导代码实施。每个阶段都必须形成可以验证的交付物，并通过退出条件后才能进入下一阶段。阶段编号表示依赖关系，不承诺固定日期。

## 2. 全程不变的约束

1. 服务器是房间状态、消息顺序、Persona、记忆写入、表情和共享语音的唯一事实源。
2. 每个房间同一时刻只有一个主写入者和一个 NEKO generation。
3. 记忆严格分为房间共享记忆、访客独立记忆和管理员保护的 Persona。
4. 普通访客不能写入 Persona，也不能读取其他访客的独立记忆。
5. 浏览器不保存 LLM/TTS 密钥、原始记忆、供应商配置或管理能力。
6. 主动主持只能由服务器端 `RoomDirector` 唯一触发，不能由每个浏览器分别计时。
7. 已删除的桌面生态、Agent、插件市场、游戏和替代渲染器不重新进入核心运行时。
8. 扩容由真实容量数据驱动；单实例满足需求时，不提前引入分布式复杂度。

## 4. 第一阶段：核心收束与单房间基线

### 4.1 阶段目标

在已有代码基础上完成增、删、改、查，最终只保留公共房间所需能力，证明一个服务器端 NEKO 可以同时服务 10–50 位访客，并保持人格、消息顺序和记忆边界一致。

### 4.2 实施范围

保留并整理：

- 文本 LLM、多供应商适配和流式输出；
- Live2D、情绪标签和共享 TTS；
- Recent → Facts → Reflections → Persona 记忆链路；
- Persona、公共事实、访客记忆和管理审核；
- SQLite/本地文件单实例持久化；
- 公网反向代理、HTTPS/WSS 和私有管理入口。

提取并重写：

- `RoomConnectionHub`：访客连接、广播、心跳、重连和序号续传；
- `RoomTurnQueue`：输入排队、幂等、限流和单写入者约束；
- `ConversationEngine`：模型调用、流式输出和故障降级；
- `MemoryFacade`：房间、访客和 Persona 三层记忆访问边界；
- `RoomDirector`：回复对象选择、冷场、频率和重复抑制；
- `AvatarState`：统一 Live2D 表情与动作状态；
- `SpeechService`：一份 TTS 结果面向全房间广播。

永久移除：

- VRM、MMD、PNGTuber、VMC 和多渲染器入口；
- Agent Server、OpenFang、浏览器/桌面控制和插件市场；
- Steam/Workshop、云存档和桌面启动器；
- 游戏、Galgame、卡片、截图/OCR、教程、成就和音乐点播；
- ASR、实时语音输入、语音克隆编辑器；
- Bilibili/Twitch/抖音、礼物、SC 和舰长逻辑；
- 浏览器端主动搭话计时器。

### 4.3 交付物

- 单个 `main` 公共房间；
- 游客 Cookie 身份和稳定 `visitor_id`；
- 多访客 WebSocket、心跳、重连和 `room_seq` 续传；
- 单写入者队列、单 generation 和 `request_id` 幂等；
- 三层记忆隔离和 Persona 写保护；
- Live2D、流式文字、表情状态和共享 TTS；
- 私有管理接口：Persona、记忆、封禁、限额、消息状态和审计；
- Nginx/systemd 部署示例、备份恢复工具和验证脚本；
- 公开资产来源、许可证和摘要清单。

### 4.4 退出条件

- [x] 核心公共房间代码闭环完成；
- [x] 桌面生态、Agent、游戏和替代渲染器完成裁剪；
- [x] LLM、Memory、TTS 单独故障时可以按设计降级；
- [x] 公网边界、安全响应头、请求体和连接上限已落地；
- [x] 数据保留、自动清理、备份与隔离恢复工具已落地；
- [ ] 真实 LLM、Memory 和至少一个 TTS 完成端到端验收；
- [x] 10、25、50 人各运行 30 分钟并保存容量证据；
- [ ] 50 人档位完成至少 24 小时稳定性运行；
- [ ] 在独立 Linux 主机完成一次备份恢复演练；
- [ ] 生产 Live2D 模型、动作、字体和公开音色取得明确授权。

上述未完成项全部关闭后，才把 `v0.1-alpha` 标记为“可公开试用”。

## 5. 第二阶段：公网 Beta 与运营闭环

### 5.1 阶段目标

让单房间从“能够部署”变成“能够持续运营”。管理员必须能发现滥用、依赖故障、成本突增和数据损坏，并能够限制影响、恢复数据和追溯原因。

### 5.2 实施范围

- 内容治理：输入/输出审核、举报、处分期限、申诉和处置审计；
- 访问控制：IP、访客、房间和供应商预算四层限流；
- 管理安全：重新认证、会话轮换、可选 MFA 和高风险操作审计；
- 可观测性：结构化日志、在线人数、队列深度、首 token 延迟、TTS 延迟和错误率；
- 成本控制：按轮记录 token/TTS 用量，设置日/小时硬预算和超额降级；
- 数据可靠性：Schema 版本、向前迁移、Persona 版本历史和一键回滚；
- 运维闭环：每日备份校验、异机恢复、告警、24/72 小时稳定性与故障注入；
- 用户体验：移动端布局、键盘操作、减少动态效果和基础无障碍支持。

### 5.3 交付物

- 统一的运营管理后台；
- 内容审核和举报处置工作流；
- 指标、日志、告警和用量看板；
- 预算熔断、慢速模式、只读和暂停策略；
- Persona 版本管理和可重复的数据迁移流程；
- 公网部署、安全复核、事故处理和恢复手册。

### 5.4 退出条件

- 目标 10–50 人房间连续运行 72 小时，无顺序破坏、死锁或不可恢复队列；
- 依赖故障和预算超额均能自动进入预定降级状态；
- 管理员能在同一后台完成发现、限流、封禁、审核、回滚和恢复；
- 所有 Persona、共享记忆和访客状态修改均有操作者、时间、原因和结果；
- 保留任务、备份恢复和告警链路均完成真实演练；
- 公网安全复核通过，非允许路由无法从公网访问。

## 6. 第三阶段：身份与长期关系

### 6.1 阶段目标

为愿意长期参与的访客提供可恢复身份和跨设备关系连续性，同时保留匿名进入能力。

### 6.2 主要交付

- 账号登录、登出、恢复和显式匿名身份绑定；
- `guest`、`member`、`moderator`、`admin` 权限模型；
- 访客查看、导出、纠正和删除自己的独立记忆；
- 记忆保存同意、保留期限和撤回机制；
- 账号删除、封禁申诉和高风险操作二次验证；
- 关系状态只从有证据的事实与反思演进。

### 6.3 退出条件

- 匿名身份升级、跨设备恢复和解绑均为可回滚、可审计事务；
- 用户只能恢复自己的数据，管理员权限严格分层；
- 导出、遗忘和账号删除在规定时限内完成；
- 不使用 IP、User-Agent、显示名或语言风格猜测身份。

## 7. 第四阶段：多房间与按需扩容

### 7.1 启动条件

只有出现真实多房间需求、单实例容量不足，或必须支持故障转移/滚动发布时才启动本阶段。

### 7.2 主要交付

- 房间创建、关闭、暂停、归档和容量配置；
- 统一 Persona 下的房间局部上下文；
- PostgreSQL 持久化、Redis 短期状态和对象存储共享音频；
- 房间 owner lease、单调 fencing token 和写入校验；
- 可独立伸缩的 Conversation/TTS worker；
- 从 SQLite 到 PostgreSQL 的校验式迁移和可执行回滚。

### 7.3 退出条件

- 主实例生成中退出时，接管不会产生双回复；
- 故障转移和重放不会产生重复 `room_seq`；
- 多实例下仍维持房间、访客和 Persona 三层记忆隔离；
- 迁移结果通过数量、摘要和语义抽样校验。

## 8. 第五阶段：1.0 产品化

### 8.1 阶段目标

把已经验证的公共房间能力包装成可嵌入博客、协议稳定、可长期维护的正式产品。

### 8.2 主要交付

- 同域链接、受限 iframe 或组件嵌入方案；
- HTTP/WebSocket 协议版本、弃用周期和升级说明；
- 管理员手册、事故响应、数据请求和维护窗口流程；
- 服务状态页、变更日志和发布检查表；
- 经授权的 Live2D/TTS 资源管理；
- 可选的直播平台消息输入适配器，仅将消息标准化为房间事件。

### 8.3 退出条件

- 完成一次 Beta 到 1.0 的真实数据迁移演练；
- 稳定性、安全、成本和恢复指标连续满足一个发布周期；
- 核心协议、隐私、保留、备份和事故处理均有可执行文档；
- 核心功能不依赖任何已经永久移除的遗留模块。

## 9. 当前执行顺序

当前只推进第一阶段的剩余验收，不提前开发第二阶段的新功能：

1. 完成 50 人档位 24 小时稳定性验证；
2. 使用费用闸门完成真实 LLM、Memory、TTS 验收；
3. 确认生产模型、动作、字体和音色授权；
4. 在独立 Linux 主机完成备份恢复演练；
5. 召开第一阶段退出评审，决定是否开始公网 Beta。

每一项必须保留命令、配置摘要、脱敏结果和失败说明。没有证据的“看起来可用”不计入阶段完成。

## 10. 变更规则

- P0：身份/记忆泄露、Persona 投毒、双写、密钥暴露、不可恢复数据损坏；必须停止发布并优先处理。
- P1：房间不可用、消息乱序、无上限成本、管理能力缺失；不得带入下一阶段。
- P2：体验优化、新供应商和运营效率；不影响当前阶段退出时按优先级实施。
- P3：尚未被真实需求证明的扩展；保持在候选列表，不进入核心运行时。

任何新功能如果削弱单写入者、记忆隔离、安全或恢复能力，必须先更新设计决策和本计划，再开始实施。
